# LTO Exam Reviewer Mobile App with Hiligaynon Translation

A driver's license exam reviewer for the Philippine Land Transportation
Office (LTO), built to help Ilonggo (Hiligaynon-speaking) drivers study
in their own language.

```
project/
  backend/                Django REST Framework API (JWT auth, questions, mock exams, PDF export)
  mobile_app/              Flutter sample client (login, exam setup, mock exam, results, offline cache)
  API_DOCUMENTATION.md     Full endpoint reference
  DEPLOYMENT.md            Local dev + production deployment (Postgres/Gunicorn/Nginx) + Flutter build
  answer_key_review_NEEDS_VERIFICATION.csv   Worklist for verifying the seeded answer key (see below)
```

## Quick start

```bash
cd backend
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python manage.py migrate
python manage.py loaddata questions_seed
python manage.py seed_demo_data
python manage.py runserver
```

Then, in another terminal:

```bash
cd mobile_app
flutter pub get
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8000/api
```

Log in with `examinee@ltoreviewer.local` / `Examinee@12345`, or register
a new account. For admin/content management, log into
`http://localhost:8000/admin/` with `admin@ltoreviewer.local` / `Admin@12345`.

Full instructions: [DEPLOYMENT.md](DEPLOYMENT.md). Full API reference:
[API_DOCUMENTATION.md](API_DOCUMENTATION.md).

## What's included

**Backend (Django + DRF)**

- Custom `User` model (email login, `admin`/`user` roles), JWT auth via
  `djangorestframework-simplejwt` (access/refresh, rotation, blacklist),
  email verification, password reset, admin-only user management
- `Question` model with English/Filipino/Hiligaynon text and optional
  images for the question and each of the three options, admin CRUD +
  bulk upload (with images), and a Django admin UI with image previews,
  bulk actions, and a "needs review" workflow for the answer key
- Mock exam engine: pick a category (Student/Non-Professional/Professional),
  a language, a question count (LTO-standard defaults, or custom),
  and an optional timer; the answer key is withheld while the exam is
  in progress and revealed only in the graded result
- ReportLab-generated PDF reviewer export, per language/category
- Transactional email for registration, password reset, and exam
  completion (console backend for dev, SMTP for production)
- OpenAPI schema + Swagger UI (`/api/docs`) generated by drf-spectacular
- 101 real LTO reviewer questions seeded from the project's existing
  `LTO-Reviewer.docx`, fully trilingual (see the answer-key note below)

**Flutter sample app**

- Login/Register screens wired to the JWT endpoints
- Home screen: category, language, question-count, and timer selection
- Mock exam runner: paginated questions, live countdown, submit
  confirmation
- Results screen: score, pass/fail, full per-question review with the
  correct answer and explanation
- Exam history
- `dio`-based API client with automatic access-token refresh
- SQLite-backed offline question-bank cache (download-once, read offline)

## ⚠️ Before you trust the seeded answer key

`LTO-Reviewer.docx` (the source content in this project's folder)
contains each question's text, options, and explanation in three
languages, but no explicit "correct answer" marker. The seed data's
`correct_answer` for each of the 101 questions was inferred
programmatically from the explanation text - **75 of the 101 were
flagged `needs_review: true`** because that inference was ambiguous, and
even the "confident" 26 should be spot-checked (the heuristic got at
least one of those wrong during testing, question #1).

Before using this for real exam prep: open `/admin/`, filter Questions by
"Needs review", and correct `correct_answer` against an authoritative LTO
reference - `answer_key_review_NEEDS_VERIFICATION.csv` gives you a
prioritized, lowest-confidence-first worklist with the English text
already pulled out so you don't have to re-read the whole reviewer doc.
See **API_DOCUMENTATION.md → Answer-key disclaimer** for the full
explanation.

## Notes on the data model

Field names were kept close to the schema already documented in this
project's `LTO-Thesis-Edited.docx` (the `users` and `questions` tables,
Appendix D/E) so this can be read as a continuation of that prior
Laravel/MySQL implementation, ported to Django REST Framework + Flutter.
Differences are called out in code comments where they matter (e.g.
`remember_token` is kept for schema parity but unused - JWT refresh
tokens do that job now).
